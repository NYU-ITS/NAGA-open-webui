# **Multi-Provider, Multimodal RAG Pipeline**

## **1\. Scope and decisions for approval**

This plan covers the implementation of the architecture defined in [`Multi-Provider, Multimodal-Ready Embedding Architecture`](https://docs.google.com/document/d/1tOLdvIdsCk2N5o173QYMyPQnDQ35Yy2NbIBUNMviW4w/edit?tab=t.0) for the current Pilot GenAI codebase. The source document remains the product and architecture specification except that its group-level model configuration is intentionally adapted here to admin-level configuration with inheritance by the admin's user groups. This document defines the implementation order, repository-specific decisions, ownership, and release process.

The goal for V1 is to remove the current dependency on one embedding provider, one model, one vector dimension, and text-only content. Each admin will select one approved embedding model from Settings. That model will apply to knowledge bases and chat file uploads associated through the existing RBAC relationships with every user group the admin owns. User groups inherit their owning admin's embedding model and do not store an independent model selection. Document ingestion and query retrieval will resolve the responsible admin's model, use the same provider adapter, and search only vectors generated by that model.

PGVector will remain the vector backend. Different embedding dimensions will use separate internal vector tables hidden behind one repository interface. When an admin changes models, retrieval for the knowledge bases and chat files governed by that admin will be unavailable while an RQ job regenerates their embeddings. Text support will be completed first; basic image support will then use the same registry, provider, job, storage, and retrieval paths.

### **Included in V1**

* One embedding provider and model selection per admin.  
* Inherited embedding configuration for every user group owned by that admin.  
* A registry of approved models, dimensions, and modalities.  
* Multiple providers behind a common embedding interface.  
* Text ingestion and model-aware query retrieval.  
* Different vector dimensions without padding or truncation.  
* Reindexing through the existing Redis Queue infrastructure.  
* Admin-visible indexing status and failed-document information.  
* Admin settings UI for viewing and changing the selected model.  
* Basic image storage, metadata, and provider-supported embedding.  
* Regeneration and migration of embeddings governed by each admin.  
* Traceability from each vector to the model that generated it.  
* Existing text knowledge RAG and chat file behavior after each admin is migrated.

### **Excluded from V1**

* Embedding version history or rollback.  
* Serving old and new embedding models simultaneously.  
* Per-knowledge-base model selection.  
* Retrieval across different admin model spaces in one request.  
* Admin-level provider credential management.  
* Hybrid search or reranking.  
* Audio or video processing.  
* New OCR or image-captioning infrastructure.  
* Dedicated Kubernetes reindex jobs.  
* Migration to a different vector database.

### **Decisions requiring approval**

* Retrieval may be unavailable for content governed by an admin while reindexing is queued, processing, failed, or partially failed.  
* Provider credentials remain platform-managed in V1. Admins select an approved model, not a credential or provider connection.  
* The initial providers, models, modalities, and dimensions will be fixed before the vector-table migration is written.  
* Existing RBAC relationships will determine the responsible admin for a user group, knowledge base, or chat file context. No separate canonical knowledge-base group will be introduced for embedding purposes.  
* Reserve existing embeddings by default after verifying their model and dimension. Add dimension-specific tables for new models.  
* Image-derived text will be used only when it is already available from a loader or provider. A new OCR or captioning service is separate work.

## **2\. Assumptions not specified in the source architecture**

The source document defines the desired product behavior but does not account for several Pilot GenAI-specific implementation details. The following assumptions must be treated as part of this plan:

1. **Admin-owned embedding configuration.** The admin account is the configuration owner. Each admin selects one approved model, and every user group the admin owns inherits that selection. Knowledge bases and chat file uploads resolve the responsible admin through existing RBAC ownership and access relationships.  
2. **Existing file records are documents.** The current `file` table will serve as the source-document entity. We will not create a second documents table.  
3. **Existing file membership remains in place.** V1 will continue using `knowledge.data.file_ids`; it will not introduce a separate knowledge-to-file association table.  
4. **Platform-level provider configuration.** Provider base URLs and API keys will continue using existing server-side configuration. An admin setting stores only an `embedding_model_id`.  
5. **Current provider first.** The first adapter will wrap the current Portkey/OpenAI-compatible text-embedding path. Additional providers will use the same interface after that path is stable.  
6. **Existing RQ infrastructure.** Reindexing will reuse the current Redis Queue and worker deployment. A dedicated queue or worker pool will be added only if measurements show that reindexing delays normal file ingestion.  
7. **One effective model space per RAG request.** If a request includes multiple knowledge bases or files, all of them must resolve through their RBAC context to the same effective admin model. The backend will reject requests that would mix embedding model spaces.  
8. **Alembic owns the new vector schema.** New PGVector tables and indexes will be created through migrations rather than dynamically by the vector adapter at startup.  
9. **Admin-by-admin rollout.** We will regenerate and validate all applicable knowledge-base and chat-file embeddings governed by one admin before moving the next admin to the new read path.  
10. **Knowledge and chat-file RAG are the project boundary.** Chat knowledge retrieval, knowledge ingestion, chat file upload ingestion and retrieval, the file worker, and the Pilot GenAI facilities RAG path are included. User-memory embeddings remain on their current policy unless a shared dependency must be updated for compatibility.  
11. **Existing RBAC remains authoritative.** The project will not add special handling for roles or users outside user groups because the current RBAC logic already handles those cases.  
12. **No new OCR or captioning service.** Image-derived text will be used only when the existing processing path or selected provider already produces it.

If any assumption is rejected, the affected schema or phase must be revised before implementation begins.

## **3\. Repository-specific design**

### **3.1 Admin and model resolution**

Every admin will have one `admin_embedding_settings` row pointing to an enabled registry model. Every user group owned by that admin inherits the admin setting; user groups do not receive separate embedding settings.

Knowledge-base ingestion, chat file ingestion, and retrieval will resolve the same admin setting through `EmbeddingService`, using the existing RBAC context to determine the responsible admin. Ingestion routes output to the table matching the registry dimension. Retrieval confirms that all requested knowledge bases and files resolve to the same effective admin model, embeds the query with that model, and filters the search by admin, model, authorized knowledge-base IDs, and authorized file IDs.

This replaces ad hoc email-based model lookup with one explicit admin setting and shared resolver. A query vector must never be compared with document vectors generated by another model.

### **3.2 Provider and embedding services**

Provider-specific request handling will move out of routers and workers. The application-facing provider interface will remain small:

class EmbeddingProvider:  
    def embed(self, inputs, model): ...

`EmbeddingService` will resolve the model, select the adapter, call the provider, and reject incorrect output counts, dimension mismatches, non-finite values, and unsupported modalities.

API keys must not be returned to the browser, logged in full or in part, or placed in new RQ payloads.

### **3.3 Data model**

| Record | Purpose | Key fields |
| ----- | ----- | ----- |
| `embedding_models` | Registry of approved models | provider, model name, dimension, modality, status |
| `admin_embedding_settings` | One selected model per admin | admin ID, embedding model ID, updated by, updated at |
| Existing RBAC ownership | Resolves inherited settings | admin ID, owned user-group context, authorized knowledge/file context |
| `rag_chunks` | Searchable text or image-derived content | admin ID, knowledge ID, file ID, chunk index, content, content type, metadata |
| `embeddings_<dimension>` | Model-aware PGVector rows | admin ID, knowledge ID, file ID, chunk ID, model ID, vector, modality, status |
| `embedding_jobs` | Initial index, reindex, and retry state | admin ID, model ID, job type, status, counts, failed file IDs, error |

`embedding_models.dimension` maps to an approved physical table such as `embeddings_1536` or `embeddings_3072`. Adding another dimension requires an Alembic migration and a repository routing entry. The product UI will show the provider and model name, not the internal vector-table name.

The new path will not pad or truncate vectors. A dimension mismatch is a hard failure recorded against the embedding job.

### **3.4 Reindex behavior**

A model change will use one selected model and one operational job:

1. The API confirms that the caller is the admin account allowed to manage its embedding setting.  
2. One transaction updates the admin model, marks embeddings governed by that admin stale, creates a queued job, and prevents another model change for that admin.  
3. The API enqueues only `job_id`; the worker resolves all other configuration.  
4. Retrieval remains unavailable while the worker processes files and updates completed and failed counts.  
5. Success deletes stale embeddings and restores retrieval. Failure remains visible and requires a successful retry or another model change.

Job execution must be idempotent. A retry will replace an existing vector for the same admin, model, and chunk rather than create a duplicate.

### **3.5 Image behavior**

An image chunk will store the image reference, MIME type, available metadata, and existing caption or OCR text. A verified multimodal adapter may embed the image directly; a text-only model may embed available derived text. If neither path is available, the file fails with an unsupported-content message. No new OCR or captioning pipeline is part of this release.

## **5\. Validation approach**

No tests are being created or run as part of planning. When test work is explicitly approved, all application and test commands must run through `docker-compose.local.yaml`.

### **Service validation**

* Correct provider selection for each registered model.  
* Correct admin setting resolution for knowledge-base and chat-file operations.  
* User groups inherit their owning admin's model without storing a separate selection.  
* Exact provider output-count and dimension validation.  
* Unsupported modality handling.  
* No secrets in responses, logs, traces, or new queue payloads.

### **PostgreSQL and PGVector validation**

* Each dimension writes to and searches the correct table.  
* Admin, model, knowledge, file, and existing RBAC filters prevent cross-space or unauthorized results.  
* Retried writes do not create duplicate rows.  
* The production pgvector version supports selected dimensions and indexes.

### **Worker validation**

* Queued, processing, completed, failed, and partially failed transitions.  
* Retry after a provider or document failure.  
* Worker restart and duplicate RQ delivery.  
* Rejection of a second model change during active indexing.

### **End-to-end validation**

* Existing text knowledge bases and chat file uploads retrieve relevant chunks after regeneration.  
* Query and document vectors use the same model.  
* Retrieval is unavailable with a clear message during reindex.  
* A successful model change updates both ingestion and retrieval.  
* Admin settings permissions, inherited group behavior, and existing RBAC restrictions are enforced.  
* Image storage and the approved image or fallback path work.

## **6\. Rollout and rollback**

Rollout will proceed one admin at a time. For each admin, we will record:

* Selected model and dimension.  
* Owned user-group, knowledge-base, chat-file, and chunk counts.  
* Job status and failed files.  
* Representative retrieval results before and after migration.  
* Query latency and embedding-job duration.  
* Decision to proceed, retry, or defer.

During rollout, rollback means returning content governed by an admin to the retained legacy read path. It does not mean switching between historical versions in the new system. Legacy cleanup will begin only after all migrated admins complete the agreed observation period.

## **7\. Main risks and mitigations**

| Risk | Mitigation |
| ----- | ----- |
| Existing RBAC context does not resolve a responsible admin unambiguously | Resolve the exception before migration; do not create a separate embedding ownership model |
| A user group is reassigned to another admin | Resolve the new admin setting and reindex affected knowledge-base and chat-file content before using the new model space |
| Query and document models do not match | Resolve both through one service and filter by model ID |
| A provider returns an unexpected dimension | Fail the job; never pad or truncate the vector |
| Reindex fails and retrieval stays unavailable | Expose the error, failed files, and retry action |
| RQ retries create duplicate vectors | Use idempotent admin/model/chunk writes |
| Reindex work delays normal file processing | Measure queue delay; add worker isolation only if needed |
| Legacy metadata identifies the wrong model | Regenerate from source files instead of copying vectors |
| Image scope expands beyond V1 | Limit work to storage, metadata, provider support, and available text fallback |
| Credentials appear in logs or queue payloads | Remove current diagnostics and resolve credentials server-side |

### Note on existing vector db

Re-embedding all existing vectors is not inherently required.

The current \`document\_chunk\` table can remain the physical store for the existing 1536-dimensional global model, while new tables are added for other dimensions. That approach matches the PDF’s “separate vector tables by dimension” recommendation.

I recommended regeneration as a conservative fallback because of two repository-specific uncertainties:

\- The current adapter pads vectors shorter than 1536 with zeros in (NAGA-open-webui/backend/open\_webui/retrieval/vector/dbs/pgvector.py:132). If only a true 1536-dimensional model has been used, this is irrelevant.  
\- Existing vectors were created under one global setting and do not provide the explicit admin attribution required by the new per-admin model resolution and filtering path. Admin provenance must therefore be audited before those rows are retained.

Those risks justify an audit, not automatic regeneration.

The better migration strategy is:

1\. Register the current production global model and its verified dimension.  
2\. Treat the existing \`document\_chunk\` table as the storage table for that model.  
3\. Keep vectors that can be attributed confidently to both the verified model and the responsible admin through existing RBAC relationships.  
4\. Map existing collections, knowledge bases, and chat files to the responsible admins through the current RBAC paths; do not create a separate canonical group assignment.  
5\. Seed every admin setting with the current global model and continue using that exact model for query embeddings against retained rows until the admin selects another model.  
6\. Add new tables such as \`embeddings\_768\`, \`embeddings\_1536\_v2\`, or \`embeddings\_3072\` as new models are enabled.  
7\. Re-embed only when:  
   \- An admin changes models.  
   \- Existing vectors cannot be attributed confidently to the registered model and responsible admin.  
   \- Existing rows were produced by different dimensions and padded.  
   \- Source content or chunking must be regenerated.

Before retaining the existing vectors, verify:

\- The table column is actually \`vector(1536)\`.  
\- All existing vectors came from the same intended global model.  
\- No alternative embedding models were used in production.  
\- Every collection, knowledge base, and applicable chat file can resolve to a responsible admin through existing RBAC relationships.  
\- Query embedding continues using that exact model.

If those checks pass, preserving the current vectors is the lower-risk and lower-cost choice. The PDF allows either migration or regeneration; regeneration is only described as cleaner when the data volume is small, not as mandatory.

Separate dimension tables are fully compatible with pgvector. Its official documentation also supports mixed dimensions in one dimensionless column, but indexes must remain dimension-specific; using separate tables is simpler and matches the PDF’s recommendation. \[[Official pgvector guidance](https://github.com/pgvector/pgvector#can-i-store-vectors-with-different-dimensions-in-the-same-column)\]
